# 01-notebook 学习笔记：数据审计、EDA 与建模前准备

面向 Python 新手 · 对照 `notebooks/01_data_understanding.ipynb` · 整理日期：2026-10-12

> 阅读方式：先读第 1—5 节，建立数据分析的整体框架；再读第 6—9 节，理解 audit 的计算、保存和展示。所有代码讲解都先介绍一般语法，再解释项目写法。标为“教学示例”的代码用于理解概念，不代表项目已经执行过这些分析。

## 1. 先把几个概念放到正确的位置

建模前的工作可以理解成连续回答几个问题：

**我要回答什么 → 数据是否可信 → 数据是什么样 → 需要验证什么假设 → 怎样评价模型 → 怎样把数据交给模型。**

“缺失值处理”“异常值处理”都是其中的局部操作，不能代替完整流程。也不是所有项目都必须填补缺失、删除异常、标准化或做一整套检验。

| 环节 | 核心问题 | 常见工作 | 留下的结果 |
| --- | --- | --- | --- |
| 业务与数据定义 | 每行代表什么？预测或估计什么？ | 确定分析单位、指标口径、时间窗口、可用特征 | 数据字典、目标和评价标准 |
| 数据质量审计 Audit | 数据有没有缺、错、重复或矛盾？ | 检查结构、类型、缺失、范围、逻辑、主键与关联 | 问题清单、统计摘要、处理记录 |
| 探索性数据分析 EDA | 分布和关系是什么样？ | 描述统计、图形、分组比较、相关性、稀疏程度 | 对数据的理解、待验证的问题 |
| 统计诊断与检验 | 观察到的差异怎样解释？ | 效应量、区间、假设检验、实验诊断 | 带有适用条件的证据 |
| 数据划分 | 将来面对什么新数据？ | 随机、时间或用户分组划分；锁定测试集 | train / validation / test |
| 预处理与特征准备 | 模型需要什么输入？ | 按需要填补、编码、缩放、变换和特征构造 | 在训练集学到的处理规则 |

Audit、EDA、统计诊断会相互交叉。例如“分组转化率”既帮助了解数据，也可以支持效果估计。分类的意义是明确目的，不是强行把每个操作只归入一个盒子。

### 一个更稳妥的实际顺序

1. 明确目标、字段含义和一行数据的含义；保护原始数据。
2. 对全量数据做结构和预先规定的质量检查，修复可以确认的格式或口径错误。
3. 尽早确定划分规则并保留测试集。数据太大时，可先进行有明确方案的抽样。
4. 主要在训练或开发数据上做深入 EDA、诊断和特征决策。
5. 只在训练集拟合填补、缩放、编码等规则；把相同规则应用于验证集和测试集。
6. 建立基准模型，用验证集选择方案；方案固定后做最终测试。

全量查看行数、字段、非法标签是质量检查；利用测试集里的相关性决定保留哪个特征，会影响模型选择。项目 01 展示了全量审计和历史摘要，不能把“看过全量描述”当成“可以用测试结果反复调模型”。预处理只在训练集学习，这是 [scikit-learn 的防泄漏建议](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage)。

## 2. Audit：先判断数据能不能被正确使用

### 2.1 先理解结构与字段

一般项目先确认：行数、列数、列名、数据类型、单位、记录粒度和记录时间。还要确认关联多个表时有没有漏行或一对多扩张。

例如：金额的单位是元还是分？一行是用户还是订单？同一个用户能出现多次吗？标签的观察窗口是否已经结束？这些问题不解决，后面的统计可能计算得很精确，含义却是错的。

本项目有 **13,979,592 行、16 个原始字段**：

| 字段 | 作用 | 如何使用 |
| --- | --- | --- |
| `f0`—`f11` | 12 个匿名的处理前特征 | 用作特征 X；不能自行编造业务含义 |
| `treatment` | 是否分配到处理组，T | 用来区分两组；分配不等于实际曝光 |
| `conversion` | 是否转化，主要结果 Y | 主结果分析 |
| `visit` | 是否访问，辅助结果 | 辅助诊断和分析 |
| `exposure` | 是否实际曝光 | 仅用于审计；发生在分配后，不能作为处理前 X 或按它筛选分析样本 |

程序后来添加的 `row_id` 是源 CSV 的行位置，不是用户 ID。因此，原文件是 16 列，带 `row_id` 的开发样本会多一列。

### 2.2 缺失值：先发现，再解释，再选择处理

要分别看：每列缺失率、每行缺失情况、不同组的缺失率，以及某些列是否经常一起缺失。注意：`NaN`、空字符串、`-999`、`"unknown"` 不一定都会被软件自动当成缺失，必须结合数据字典。

| 情况 | 可考虑的办法 | 需要注意 |
| --- | --- | --- |
| 少量、原因清楚的损坏记录 | 修复来源；必要时排除并记录原因 | 不能只凭“比例小”认定没有偏差 |
| 数值特征缺失 | 中位数填补、模型支持的缺失处理、缺失标记 | 中位数从训练集学习；填补改变分布 |
| 类别特征缺失 | 单独设为“未知”类别或适当填补 | “未知”是否有业务含义需要确认 |
| 整列大量缺失 | 查采集原因，评估保留价值 | 没有通用的“超过某比例必须删”规则 |
| 结果标签缺失 | 核对观察窗口或采集问题 | 不要把未知结果随便填成 0 |

有时会用 MCAR、MAR、MNAR 描述缺失机制。初学阶段先记住：**缺失是否与人群或结果有关，会影响处理后的结论；仅靠观察到的数据通常不能完全确定缺失机制。**

项目的 `missing_or_nonfinite = 0` 表示所有原始字段通过了有限数值检查。这里包含缺失数值以及正、负无穷。代码没有进行填补，而是遇到这类值就终止，让分析者先明确处理方案。

### 2.3 异常值：三种东西要分开

| 类型 | 例子 | 优先处理 |
| --- | --- | --- |
| 不符合定义的错误 | 二元标签出现 2；金额单位混乱 | 查来源、修复或按规则排除 |
| 违反数据逻辑的记录 | 项目约定下转化为 1、访问却为 0 | 核查口径、关联和采集过程 |
| 少见但可能真实的极端值 | 长尾收入、匿名特征特别大 | 先观察和解释，再决定是否变换或处理 |

常见的异常候选识别办法：

- **业务范围**：例如年龄不能是负数；前提是字段确实表示年龄。
- **分位数和图形**：查看 P1、P50、P99、最大最小值、直方图、箱线图。
- **IQR 规则**：IQR = Q3 − Q1；把低于 Q1 − 1.5×IQR 或高于 Q3 + 1.5×IQR 的值标为候选。
- **Z-score**：看偏离均值多少个标准差；分布强烈偏斜时，固定的“3 个标准差”规则可能不合适。
- **MAD 等稳健尺度**：减少均值和标准差受极端值影响的问题；大量相同数值也可能使尺度为 0。

这些主要是筛查规则，**不会自动证明数据错误**。截尾、删行、对数变换都是后续决策，还要考虑它们是否改变了分析人群及估计目标。数据驱动的阈值从训练集确定。

项目中 `f9` 的百万样本统计：中位数约 13.19，最大值约 75.30；这是右侧尾部的线索。`f1` 的 Q1、Q2、Q3 都约为 10.06，说明数值很集中，IQR 可能为 0 或很小，直接套规则可能标出大量记录。字段匿名，没有业务依据认定这些值错误，所以本项目没有看到自动删除或截尾步骤。

### 2.4 重复、主键和独立性

一般要分别问：整行是否重复？业务主键是否重复？同一实体是否有多条合理记录？重复是否来自拼接或重复入库？

项目的 `duplicate_row_fingerprints = 1,259,545` 是：

**总行数 − 唯一全字段哈希数。**

它统计“相对于每种记录保留一份，多出来多少条”，约占全量 9.01%；不是“重复用户数”，也不是“所有处于重复组的行数”。例如同样一行出现 3 次，这个统计增加 2。

64-bit 哈希把一行压成短指纹，便于比较，但存在很小的碰撞可能。匿名字段相同也不代表同一个人；没有用户 ID，项目只披露诊断，不自动去重。

### 2.5 项目的逻辑检查

| audit 字段 | 当前值 | 回答的问题 | 不能推出什么 |
| --- | --- | --- | --- |
| `n_rows` / `n_columns` | 13,979,592 / 16 | 扫描了多少原始记录和字段 | 不等于训练用了这么多行 |
| `n_treatment` / `n_control` | 11,882,655 / 2,096,937 | 两组各有多少行 | 不要求两组人数相等 |
| `treatment_ratio` | 约 0.85000013 | 公开样本的处理组占比 | 不是已知的原始实验设计比例 |
| `missing_or_nonfinite` | 0 | 数值有限性检查是否通过 | 不代表所有质量问题都不存在 |
| `invalid_binary_labels` | 0 | T、conversion、visit、exposure 是否都是 0/1 | 不代表标签语义必然正确 |
| `control_exposed` | 0 | T=0 且 exposure=1 有多少条 | T=1 并不意味着每个人都曝光 |
| `conversion_without_visit` | 0 | conversion=1 且 visit=0 有多少条 | 不证明整条业务链没有其他问题 |
| `duplicate_row_fingerprints` | 1,259,545 | 全字段重复指纹的多余行数 | 不能认定重复用户或直接删行 |
| `sample_n` / `sample_seed` | 1,000,000 / 42 | 开发样本大小和随机种子 | 与全量审计行数不同 |

这里大多是**确定性检查**：直接核对定义与规则，不需要 p 值，也不需要训练机器学习模型。

## 3. EDA 到底包含什么？

EDA 是 Exploratory Data Analysis，探索性数据分析。它通过统计和图形理解数据、发现模式、提出问题；不是“做几张图”就结束，也不等于正式证明假设。

### 3.1 单变量：一个字段自己是什么样？

数值字段看数量、均值、标准差、分位数、范围、偏斜、长尾、集中点和近乎常数的列。图形可以用直方图、箱线图、经验累积分布图（ECDF）。类别字段看各类别的数量、比例、稀有类别和取值数。

项目 01 的 `sample[FEATURES].describe().T` 展示每个特征的 count、mean、std、min、25%、50%、75%、max。直方图中 `log=True` 使用的是**纵轴计数的对数刻度**，帮助看清少数记录；没有对原始特征做 log 变换。

### 3.2 双变量与分组：两个东西之间有什么关系？

| 想看的关系 | 常见查看方式 | 解释边界 |
| --- | --- | --- |
| 数值与数值 | 散点图，Pearson / Spearman 相关 | 相关不能证明因果；低相关不排除非线性关系 |
| 类别与数值 | 分组均值、分位数、箱线图 | 关注各组样本量和差异大小 |
| 类别与类别 | 交叉表、分组比例、堆叠条形图 | 比例要说明分母，不能只看计数 |
| 特征与结果 | 按特征分箱看转化率 | 每箱都要看样本数与正事件数；探索性发现需验证 |
| 处理组与对照组 | 比较处理前特征分布、SMD、ECDF | 平衡诊断不能单独证明因果识别成立 |

更复杂的项目还看多个字段的组合、不同时间或渠道、地区人群以及数据漂移。本数据没有时间、用户或渠道等可解释字段，不能凭空补做这些分析。

### 3.3 结果稀疏性：不仅看总行数，也看有效事件数

全量 audit 的 `groups` 给出：

| 组别 | 行数 | 转化数 | 转化率 |
| --- | --- | --- | --- |
| 对照组 T=0 | 2,096,937 | 4,063 | 约 0.19376% |
| 处理组 T=1 | 11,882,655 | 36,711 | 约 0.30895% |

转化是稀疏事件。百万样本的对照组只有 273 个转化；划分后，train / validation / test 的对照转化数分别是 **164 / 54 / 55**。这比“我们有一百万行”更直接地说明某些局部效果估计为什么会不稳定。

不应为得到漂亮比例就随意重采样。用于效果估计和策略评价的数据若改变了两组或结果类别的构成，需要重新考虑权重、估计口径和抽样偏差。本项目的开发样本是全文件等概率无放回抽样。

### 3.4 特征分布与两组平衡

`feature_stats` 中各字段的含义：

| 字段 | 含义 |
| --- | --- |
| `feature` | 特征名称 |
| `min` / `max` | 全量数据中该特征的最小 / 最大值 |
| `mean_0` / `mean_1` | 对照组 / 处理组均值 |
| `std_0` / `std_1` | 对照组 / 处理组样本标准差 |
| `smd` | 处理组减对照组的标准化均值差 |

项目采用：**SMD = (mean₁ − mean₀) / √[(std₁² + std₀²)/2]**。

直觉是把两组均值差放到“标准差”这个共同尺度上比较。符号表示方向，绝对值表示差异大小。比如 f3 的 SMD 约 −0.04884，表示处理组均值较低，差约为共同尺度的 0.049 倍。

全量 12 个特征中最大的 |SMD| 约 **0.04884**，说明这些特征的均值差较小。但 SMD 没有检查全部分布形状、特征组合或未观测因素。“|SMD| < 0.1”只能作为常见经验参考，不能当作随机化成功的证明。

### 3.5 一次 EDA 应交付什么？

至少形成几个可行动的结论：哪些字段可用、哪些问题需要修复、分布有什么特点、结果有多稀疏、下一步要验证什么。每个结论应附统计或图形，并说明对分析的影响。

本项目可得到：数值与标签检查通过；存在重复匿名记录但依据不足以去重；部分特征高度集中且有尾部；转化事件很少，尤其是对照组；处理前均值差较小，还需开发集上的分布和组合诊断。

## 4. 具体检验方法：先问问题，再选方法

不需要对每一列都套一遍所有检验。检验选择取决于变量类型、研究问题、样本是否独立、是否配对，以及实验或抽样设计。

### 4.1 常用方法对照表

| 问题 | 首先看什么 | 可用方法 | 主要条件与边界 |
| --- | --- | --- | --- |
| 两组连续变量均值是否不同？ | 均值差、标准差、样本量、区间 | Welch 两独立样本 t 检验 | 独立样本；小样本下注意分布和极端值；不要求两组方差相等 |
| 两组连续或有序变量的秩 / 分布是否不同？ | 箱线图、ECDF、分位数 | Mann–Whitney U | 独立样本；一般不能简单说成“中位数检验”；并列值影响计算 |
| 两组分布形状是否不同？ | ECDF、KS 统计量 D | 两样本 KS | 标准检验假设连续分布；大量并列值时 p 值解释需要谨慎 |
| 两个类别变量是否有关？ | 交叉表、比例差 | 卡方独立性检验 | 独立观测；看期望频数，小频数时渐近近似可能不好 |
| 2×2 表很稀疏时怎么办？ | 原始事件数 | Fisher 精确检验等精确方法 | 检验表中的关联；仍需效应量和区间解释业务意义 |
| 两组转化率是否不同？ | 两组转化率、绝对差、区间 | 两比例 z 检验；稀疏时考虑精确方法 | 独立的二元结果；正、负事件数需支持正态近似 |
| 分组人数是否符合实验设计？ | 设计比例、观察人数 | SRM：卡方拟合优度或二项检验 | 必须有事先给定的设计比例及与之匹配的抽样机制 |
| 多个 X 合起来能否预测 T？ | 留出数据的预测 AUC | C2ST 分类器双样本检验，配合置换 | 使用独立评估；置换方式须尊重分层 / 分块等设计 |

方法说明可查 [Welch t 检验](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.ttest_ind.html)、[Mann–Whitney U](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.mannwhitneyu.html)、[KS](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.ks_2samp.html)、[卡方独立性检验](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.chi2_contingency.html) 和 [Fisher 精确检验](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.fisher_exact.html) 的 SciPy 官方文档。

这些方法多数要求观测独立。同一用户重复记录、时间依赖或按群组分配实验时，要使用与结构对应的分析，不能只因为行数很大就忽略独立性问题。

### 4.2 p 值应该怎样理解？

以“两组均值相同”为零假设 H₀。p 值表示：**如果 H₀ 和检验条件成立，得到当前这么极端或更极端统计量的概率。**

它不是“H₀ 为真的概率”，也不是“差异由偶然造成的概率”。p 很小不表示效果很大；p 不小也不证明两组相同。几百万行中很小的差异也可能显著。

因此要同时看：**差异大小 + 区间 + p 值 + 数据质量与设计**。探索许多特征、分组和结果时会有多重比较问题；若要正式下结论，应预先说明检验范围，并按目的考虑 Holm 或 FDR 等校正，或用独立数据验证。

### 4.3 本项目已经做了哪些诊断？

- 全量 `audit.json`：质量计数、两组结果摘要、特征范围和两组 SMD。
- `balance.csv`：训练集的 SMD 和 KS 统计量、p 值；代码明确把它们当作探索性诊断。匿名特征中大量相同值使标准连续 KS 的 p 值更需要谨慎解释。
- `c2st.csv` 和 `c2st_null.csv`：用 X 预测 T，比较留出 AUC 与重新拟合的置换零分布。只用于开发数据诊断；不显著不能证明随机化。
- `srm.json`：本轮正式 SRM **跳过**，因为不知道设计处理比例。不能拿观察到的 85% 当作它自己的零假设。
- `ate_full.csv`：用两组聚合转化数和人数计算平均差、标准误、区间和两比例检验 p 值。它是另一个文件，不是 `audit.json` 里的一张表。

本项目展示的公开数据经过特殊子采样，结论针对公开样本中的处理分配效果。随机化、抽样、特征时点、独立性等条件要结合数据生成过程判断，无法靠一个检验全部确认。数据背景见 [Criteo 官方介绍](https://ailab.criteo.com/criteo-uplift-prediction-dataset/) 及项目 notebook 的适用范围说明。

### 4.4 怎样解读这里的转化率差？

全量转化率：处理组约 0.30895%，对照组约 0.19376%。差为约 **0.11519 个百分点**，等价于比例值约 0.00115187。在本项目的公开样本口径和相关假设下，对应约每 10 万人 115 个增量转化。

相对提升约为 **59.45%**，计算的是“绝对差 ÷ 对照组转化率”。0.11519 个百分点和 59.45% 回答不同问题，不能混写成“提升 0.11519%”而不说明口径。

这只是平均效果摘要，不能告诉你该优先联系哪些用户，也不能把处理组里转化的人直接视为“被广告说服的人”。后者需要后续 uplift 建模与策略评价。

### 4.5 一个具体的检验调用例子

**一般语法：先把样本交给检验函数，再读取返回结果的属性。**

```python
结果 = 检验函数(样本A, 样本B, 参数名=参数值)
print(结果.statistic)
print(结果.pvalue)
```

`statistic` 是检验统计量，`pvalue` 是 p 值；函数返回的对象可以通过点号读取属性。

**可运行的教学例子：两组虚构连续数据，使用 Welch t 检验。** 这不是项目转化率的分析；这里演示的是函数调用，实际使用仍需核对独立性及分布条件。

```python
from scipy.stats import ttest_ind

group_a = [1, 2, 3, 4, 5]
group_b = [2, 3, 4, 5, 6]
result = ttest_ind(group_a, group_b, equal_var=False)

print("t 统计量：", result.statistic)
print("p 值：", result.pvalue)
```

`equal_var=False` 表示不采用两组方差相等的假设，使用 Welch 方法。两组均值分别是 3 和 4，但每组只有 5 个观测。该例的双侧 p 值约为 0.347，表示在这个检验框架下不能拒绝均值相等的零假设；它没有证明两组均值相同。

## 5. 数据划分与预处理：先确定评价方式，再学习处理规则

### 5.1 怎么划分？

| 数据或部署情景 | 通常应考虑 |
| --- | --- |
| 独立、同分布的行；未来也来自类似总体 | 随机划分；稀疏类别可分层 |
| 用过去预测未来 | 按时间划分，避免未来信息进入过去 |
| 同一个人或设备有多行，评价新实体泛化 | 按用户或实体分组隔离 |
| 多个地点或实验存在群组结构 | 与群组和部署目标一致的划分 |

项目采用 **60% train / 20% validation / 20% test**，按 `T × conversion` 的四种组合分层：对照未转化、对照转化、处理未转化、处理转化。分层保持各集合的事件构成大致一致；它不会消除原本的转化稀疏问题。

没有用户 ID，本轮按行划分。验证集和测试集中约 1.8575% / 1.856% 的特征向量能匹配训练集，口径是模型使用的 float32 表示。这与全量、全 16 字段、float64 的重复指纹统计不同；不能直接比较两个比例。后续特征组隔离敏感性分析在 notebook 06。

### 5.2 哪些预处理是按需要做的？

| 处理 | 什么时候考虑 | 本项目情况 |
| --- | --- | --- |
| 缺失填补 | 模型不接受缺失，且填补方案合理 | 原始扫描无缺失；logistic 管线仍配置中位数填补器 |
| 类别编码 | 有类别字段需要转成模型输入 | 当前 X 为匿名数值特征，没有单独的类别编码步骤 |
| 标准化 | 线性模型正则化、距离计算等对尺度敏感 | logistic 管线包含 StandardScaler |
| 对数或其他变换 | 偏斜、尺度或关系需要处理 | 不能因看见长尾就认定必须变换；有负值时也不能直接取 log |
| 异常截尾 | 有明确业务 / 稳健性理由 | 当前扫描没有自动截尾步骤 |
| 特征选择或构造 | 有可验证的信息增益或业务逻辑 | 使用 f0—f11；exposure 不加入 X |

这里“通用的数据准备”与“标准化 / 归一化”不同。标准化只是一个具体变换：常见形式为 (x − 训练均值) / 训练标准差；归一化有时指缩放到 [0,1] 或单位长度，应说明具体定义。它们都不能保证变换后的数据服从正态分布。

### 5.3 为什么只能从训练集学习？

例如填补器学习训练集中位数，缩放器学习训练均值和标准差。验证和测试数据都使用这些已经确定的数值，不各自重新计算。否则评价数据参与了规则学习，或者输入尺度不一致。

模型训练以后仍可能发生泄漏：反复看测试效果改模型；根据测试结果挑阈值、预算或分群；用只有结果发生后才能取得的字段预测结果。防泄漏贯穿整个项目。

**一般语法：创建对象，然后调用对象的方法。**

```python
对象 = 类名(参数名=参数值)
训练结果 = 对象.fit_transform(训练数据)
新结果 = 对象.transform(新数据)
```

“类”可以理解为创建工具的模板；创建出的“对象”保存学到的规则。`fit` 学规则，`transform` 用规则，`fit_transform` 先学再应用。

**教学示例：数值特征预处理。** 以下代码要求已有 `X_train`、`X_validation`、`X_test`；不是独立可运行脚本。

```python
from sklearn.impute import SimpleImputer
from sklearn.preprocessing import StandardScaler
from sklearn.pipeline import Pipeline

preprocessor = Pipeline([
    ("imputer", SimpleImputer(strategy="median")),
    ("scaler", StandardScaler()),
])

X_train_ready = preprocessor.fit_transform(X_train)
X_validation_ready = preprocessor.transform(X_validation)
X_test_ready = preprocessor.transform(X_test)
```

`from 模块 import 名称` 是导入工具；`Pipeline` 按列表顺序串联步骤。列表里的每个 `(名称, 工具对象)` 是一个二元素元组。这里只用训练集学习，再把相同流程应用于其余数据。项目的 logistic 模型把填补、缩放和分类器串在同一个 Pipeline 中，具体实现见 `criteo_uplift/models.py`。

## 6. 为什么 JSON 里只有数值，没有计算函数？

你的直觉里“应该先计算，再得到结果”是对的。这里已经有函数，只是 notebook 读取的是函数以前运行后保存下来的结果。

### 6.1 三个层次，分别负责不同事情

| 层次 | 项目位置 | 负责什么 |
| --- | --- | --- |
| 计算规则 | `criteo_uplift/data.py` 的 `scan_and_sample()` | 读取原始 CSV、分块检查、累积统计、抽样、返回结果 |
| 运行与保存 | `run_pipeline.py` | 调用函数或复用校验过的缓存；保存 audit 和其他结果 |
| 读取与展示 | `notebooks/01_data_understanding.ipynb` | 找到结果目录，读 JSON / CSV，再显示表和图 |

流程可以记成：

**原始 CSV → 函数计算 → Python 字典 → 保存为 audit.json → notebook 读取 → 表格展示。**

JSON 是数据交换格式，可以保存数字、字符串、列表、对象等数据结构，不能直接保存可执行的 Python 函数。它像计算完成后的一张成绩单；`.py` 中的函数像批改和计分规则。统计 min、max、均值只需要计算规则，不需要先拟合预测模型。

### 6.2 为什么要把结果单独保存？

全量原始文件约 3.25 GB，有近 1400 万行。若打开 notebook 就重新扫描和训练，阅读成本会很高。保存聚合结果便于重复展示、对比和审计，也允许没有原始数据的人查看公开快照。

`result_directory()` 默认优先读取本地 `artifacts/`，找不到则读取 `reports/published/`；环境变量 `CRITEO_RESULTS_MODE=published` 会强制使用公开快照。01-notebook 当前保存的执行输出显示读的是 **`reports/published/conversion_1000000_seed42`**。以后重新执行可能读到另一个目录，要以实际打印的 `RUN` 为准。

当前显示的值是历史运行的摘要。读取 JSON 不会自动验证今天的原始数据是否变化，也不会重新计算。重新执行 pipeline 时，缓存复用会核对源文件 SHA256、样本大小和 seed；不满足条件则重新扫描。现有快照与当前源代码可能来自不同时间，例如当前函数增加了 `smd_status` 字段，旧快照里没有该字段。

一对方括号包围字符串会选出一列；外层方括号里再放一个列名列表，会选出多列表格。`groupby()` 分组，`agg()` 指定对每组做哪些聚合。

## 8. 真正的 min、max、mean 是怎样算出来的？

实际函数入口是 `criteo_uplift/data.py` 的 `scan_and_sample()`。不必一下子掌握它全部的抽样和数组语法，先理解“分块累积”的统计思路。

### 8.1 分块读取为什么能得到全量统计？

假设一个文件分三块，每块都读到了，就能把每块的统计合并：

- 全量行数 = 各块行数相加。
- 全量最小值 = 各块最小值中的最小者。
- 全量最大值 = 各块最大值中的最大者。
- 全量均值 = 全量总和 ÷ 全量数量。
- 标准差需要数量、总和和平方和等信息；项目按两个处理组分别累积。

**不能直接平均每块的均值**，除非每块行数相同。比如第一块 [0, 10]，第二块 [100]，块均值是 5 和 100；它们平均为 52.5，但正确全量均值为 110/3 ≈ 36.67。

项目默认每块 250,000 行；审计数值用 float64，抽样后特征转为 float32，降低建模样本的内存占用。分块减小了读入和计算时的压力，但重复指纹等辅助数据仍需内存，不能理解成整个程序的内存永远固定。

### 8.2 先学循环累积的一般语法

**一般语法：**

```python
累计量 = 初值
for 一块 in 多块数据:
    累计量 += 这一块的统计量
```

`+=` 表示“取原值加上右边，再赋回去”。循环中缩进的语句会对每一块重复执行。

**可运行的纯 Python 教学例子：**

```python
chunks = [[0, 10], [100]]
n = 0
total = 0
minimum = float("inf")
maximum = float("-inf")

for chunk in chunks:
    n += len(chunk)
    total += sum(chunk)
    minimum = min(minimum, min(chunk))
    maximum = max(maximum, max(chunk))

audit = {
    "n_rows": n,
    "min": minimum,
    "max": maximum,
    "mean": total / n,
}
print(audit)
```

正无穷作为最小值的初值，第一块的真实最小值一定会替换它；负无穷作为最大值初值同理。这样不用预先猜测数据范围。

### 8.3 对照项目中的 NumPy 写法

**一般语法：二维数组用 `[行选择, 列选择]` 取内容。**

```python
部分 = 数组[:, :列数]
每列结果 = 部分.min(axis=0)
```

`:` 表示该维全部；`:12` 表示索引 0—11，共 12 列。`axis=0` 在二维数组中表示沿行方向汇总，留下每一列的结果。索引从 0 开始。

**项目中的计算：**

```python
values = chunk.to_numpy()
x = values[:, :12]

minimum = np.minimum(minimum, x.min(axis=0))
maximum = np.maximum(maximum, x.max(axis=0))
```

`to_numpy()` 把 pandas 表格转换成 NumPy 数组。`x.min(axis=0)` 得到当前块 12 个特征各自的最小值；`np.minimum` 将它们与已有的 12 个累计最小值逐个比较。最大值同理。

最后函数把累计值放入字典，例如：

```python
row = {"feature": f, "min": minimum[j], "max": maximum[j]}
```

这不是手填的统计结果，而是从已经计算好的数组中取第 j 个特征的结果。

### 8.4 为什么有两个检查结果是直接写 0？

这是观察源代码时特别值得注意的细节。

**一般语法：条件成立时抛出异常，停止正常执行。**

```python
if 错误条件:
    raise ValueError("说明错误原因")
```

`not` 取逻辑反；`.all()` 判断是否所有元素都为真。

**项目代码的核心检查：**

```python
if not np.isfinite(values).all():
    raise ValueError("存在 missing/non-finite，请先明确处理方案")

if not np.isin(values[:, 12:], [0, 1]).all():
    raise ValueError("标签必须为0/1")
```

`np.isfinite` 对每个值判断是否有限；`np.isin(..., [0, 1])` 判断是否属于允许的标签集合。原始数组第 12 列开始，是 4 个标签字段。

只有所有块都通过检查，程序才会走到：

```python
audit = {
    # 此处省略其他字段
    "missing_or_nonfinite": 0,
    "invalid_binary_labels": 0,
}
```

因此这两个 0 是“检查通过后的固定结果”，没有单独累计错误数。如果原始数据含非法值，这次运行会报错，不会返回一份带非零错误计数的完整 audit。其他字段，如 `n_rows`、min、max、逻辑矛盾数量，是实际累积计算得到的；`n_columns=16` 则是精确校验列名后记录的预期结构。

如果希望“即便有错误也继续扫描并报告每列错误数”，需要另一种审计函数设计：累计问题、保存位置，再决定是否允许下游建模。当前项目采用检查失败即停止的设计。

### 8.5 从函数返回结果，到 pipeline 写文件

**一般语法：函数返回两个值时，可以用两个变量接收。**

```python
def 函数名():
    return 结果1, 结果2

变量1, 变量2 = 函数名()
```

这叫“解包”。`return sample, audit` 实际返回包含两个元素的元组；左右位置一一对应。

**项目调用关系：**

```python
# run_pipeline.py：需要新扫描时
sample, audit = scan_and_sample(args.data, args.sample_size, args.seed)

# run_pipeline.py：保存本次运行的审计结果
write_json(audit, out / "audit.json")
```

`args.data` 等属性来自命令行参数对象。第一行得到逐行样本和聚合字典，第二行调用项目自己的 JSON 写入函数。`write_json()` 内部将 NumPy 数值等转换成可序列化对象，再用 `json.dumps()` 写文本。

若满足缓存复用条件，pipeline 会读取之前的样本和 audit，不必每次重新扫描。函数负责定义计算规则，JSON 负责保存某次运行的结果，notebook 负责展示。

### 新手阅读时的六个自检问题

1. 我现在看到的是逐行原始数据，还是之前保存的聚合结果？
2. 统计基于全量、百万样本，还是某个 train / validation / test？
3. 这个数的分母是什么？比例值、百分比、百分点有没有区分？
4. 这个操作是在检查问题、描述数据、检验假设，还是修改数据？
5. 处理规则有没有从验证集或测试集学习？
6. 结论有没有超出匿名字段、抽样方式和实验设计支持的范围？
